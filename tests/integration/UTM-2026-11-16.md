## Build and observed fixes

Restored cloud bundle based on `160c2408a3d0893261590c41b329a2f5dec937b4`.
The shipping build rejects 26.10 before installation or Keel state creation.
For exploratory integration only, a **guest-local copy** extends the release guard
with 26.10. The restored source retains the shipping 24.04/26.04 guard. No session,
policy, freshness or recovery gate was bypassed.

Initial live testing found two compatibility faults:

1. `ss -Hltn` includes State before Recv-Q/Send-Q/local endpoint. The old parser
   read Send-Q as the endpoint and incorrectly rejected the live SSH listener.
   Corrected the column selection and require LISTEN; added IPv4/IPv6, queue-value
   false-positive and established-socket negative regressions using real format.
2. This OpenSSH version emits effective keywords such as PermitRootLogin rather
   than permitrootlogin. Effective-policy comparisons now ignore case while still
   requiring exact full-line values. Added positive, unsafe-value and missing-field
   cases. This avoids claiming success from an incomplete policy.

Both fixes are in restored source and installed VM test runtime. No commit/push.

## Interactive Tailscale SSH continuation

Actual interactive login uses a different privileged process layout from a remote
command: root `/usr/bin/login`, a root Tailscale session monitor, and the root
service daemon. On this Ubuntu build login clears its environment. Its root-owned
logind session still identifies the exact login PID as Leader, UID/name, PTY,
remote address, service and scope. Root-daemon journal entries join that PTY launch
to its session ID and then to the original authenticated connection.

The adapter now accepts this strictly correlated layout. It requires unique
records near login birth, the expected shell-only launch arguments, the actual
service MainPID and root ancestry. It rejects missing, conflicting or ambiguous
evidence. Caller SSH environment values remain untrusted. Authentication freshness
uses the original connection timestamp, including for a later multiplexed channel.
Unsupported direct remote commands still fail before restrictive changes.

Observed live results using the Tailscale host-key-verifying client wrapper:

- Interactive identity-mode verify, guarded secure and a fresh-connection confirm
  passed with actual password-authenticated administrator sudo.
- A new channel on an authenticated connection opened before hardening failed
  confirmation. The harness checked the explicit remote command exit marker;
  transport exit status alone was insufficient for this login implementation.
- A fresh IPv6 interactive login verified despite a deliberately forged caller
  SSH_CONNECTION value; evidence came from privileged records.
- Public OpenSSH recovery access was retained during investigation. No tailnet
  policy or other device was changed.

The continuation also found that the security fingerprint depended on forwarded
locale through shell glob ordering. `keel_security_digest` now fixes LC_ALL=C,
COLUMNS=80 and TERM=dumb before enumeration and command output. A disposable test
baseline reset preceded generating a new fingerprint; no mismatching policy was
silently adopted. Locale/terminal regression coverage was added.

Smoke tests, all 21 fixture groups and ShellCheck 0.11 passed inside this VM
again after the final duplicate-launch-flag tightening. The final session and
transaction modules were installed with mode 644 and their SHA-256 hashes matched
the tested source. An actual fresh interactive Tailscale SSH login then passed
Keel verification and sudo authentication with the final module (remote exit
marker 0). Public-key management intent was restored, Tailscale SSH was disabled,
and a fresh public-key login also passed verification. No transaction was pending.

## Warm-reboot control and checkpoints

Luna created `Keel Fixed Tailscale 20261116` after the successful continuation and
public recovery verification, preserving the working guest. She then restored
`Keel Test Access 20261116` for an independent control. Fresh Install and all saved
checkpoints were preserved without overwrite or deletion.

The control verified that Keel paths were absent and UFW inactive before running
normal `systemctl reboot`. Its boot ID was
`b9f4149b-7cb8-41df-a46f-59378644d5e6`; the kernel reported reboot mode `cold`.
No new boot became reachable at the known SSH address during a 150-second observer
window (20 attempts). UTM remained Started with “Display output is not active.”
This reproduces the stall without Keel installed; it does not identify the platform
cause. Luna subsequently force-stopped the hung control and cold-started it;
SSH returned with boot ID `67ef9f07-a60a-4c99-90eb-8b19648ea8b1`.

Stopped-VM inspection found one non-removable VirtIO qcow2 system disk and no
installer ISO/removable media. ARM64 UEFI Boot was enabled. No drive or firmware
setting changed. The control's clean guest poweroff succeeded.

UTM issue [#8009](https://github.com/utmapp/UTM/issues/8009) reports this version's
multicore ARM warm-reboot stall, and merged upstream
[fix #8121](https://github.com/utmapp/UTM/pull/8121) addresses HVF GIC reset. This is
a plausible platform explanation, not yet a demonstrated cause for this VM.
Luna changed the original empty/default QEMU Machine Properties to
`kernel-irqchip=off`, saved, and reopened settings to verify persistence. Hypervisor
remained enabled. Ubuntu cold-booted and SSH returned with boot ID
`c35aa683-5aed-4215-8e6a-6b566a4e97dc`; all eight CPUs were online.

The next normal no-Keel reboot still failed to return at the known SSH address
within 150 observer seconds (20 attempts). This workaround has therefore not
resolved this VM's observed stall. No second success trial was claimed.

Luna force-stopped the stalled control, removed `kernel-irqchip=off`, restored
`Keel Fixed Tailscale 20261116`, and resumed it. SSH and its fixed-checkpoint marker
were verified. Final modules and fixtures were then tested as described above.

Luna cleanly changed only CPU Cores from the original empty/default setting
(which exposed eight online guest CPUs) to **1**, saved, reopened System settings
to verify persistence, and started the same VM. QEMU Machine Properties remained
empty/default, Hypervisor/UEFI stayed enabled, memory remained 4 GB, and no disk,
network or display setting changed. Guest `getconf _NPROCESSORS_ONLN` confirmed 1.
No host app update or host security change was made.

The guest returned with boot ID `a0f90836-6d6c-427a-813c-d8a7440b065d`.
Two consecutive normal guest-initiated reboots then passed without UTM intervention:

- First returned as `91f42abc-a244-48ff-8c42-1f206fe71b27`; the SSH observer
  detected the new boot after 13.7 seconds, on attempt 3.
- Second returned as `b2a63ec8-596e-42a8-af28-d78ab982dcbb`; the observer
  detected the new boot after 14.1 seconds, on attempt 3.

A normal CLI public-key verify/secure applied a real web-profile transition from
the private baseline and left it awaiting confirmation. Transaction
`1794861310-2245-15473` had the independent recovery service enabled and visible
IPv4/IPv6 web grants before reboot. Normal `systemctl reboot` returned with boot
ID `2860f987-d77d-432e-8b14-0730a66b47be`, detected after 14.0 seconds/3 attempts.

On that warm boot, `keel-recovery.service` finished with Result=success and
ExecMainStatus=0. Pending state cleared, the transaction phase became rolled_back,
and comparisons matched the exact SSH drop-in, complete UFW tree and
`/etc/default/ufw` backup bytes. UFW file/directory modes and ownership also matched.
Only the original IPv4/IPv6 management grants remained. This validates independent
boot recovery on an ordinary warm reboot in the one-CPU configuration, without a
host power cycle or snapshot restore. The private intent was then prepared again. Final normal CLI verification,
application and independent fresh-connection confirmation all passed. A final
root check found no pending transaction, matching intent/policy fingerprints,
RunSSH=false and the expected key-only effective OpenSSH settings. Fresh IPv6
key SSH reached the same final boot ID.

The one-CPU setting resolves the stall in these observed runs. Multicore behavior
remains unresolved; this is a VM workaround, not a claim that the upstream platform
fault has been fixed. Existing saved memory snapshots predate the CPU change;
restore their original empty/default CPU setting before loading their memory.
